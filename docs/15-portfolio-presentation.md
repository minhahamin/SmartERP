# 15. 포트폴리오 발표 자료

> 이 문서는 **실제 구현 기준**이다. (Gemini 2.5 Flash Function Calling / Railway 배포 / 키워드 기반 문서 검색)
> 초기 목표 설계(OpenAI·LangChain·pgvector RAG·AWS)는 `09`~`11`, `13`~`14` 문서에 남아 있고, 구현과의 차이는 README의 "아키텍처" 표에 정리했다.
> 발표/면접에서는 "처음엔 이렇게 설계했고, 범위를 이렇게 줄여 구현했다"는 트레이드오프까지 같이 설명하는 것을 전제로 한다.

## 15.1 30초 엘리베이터 피치

> "ERPilot은 ERP와 AI 어시스턴트를 결합한 SaaS입니다. ChatGPT를 ERP에 그냥 붙인 게 아니라, **AI가 호출하는 도구의 노출과 실행 두 단계 모두에서 서버가 사용자 권한을 다시 검증**하도록 만든 게 핵심입니다. 그래서 일반 직원이 AI에게 타인의 급여를 물어도 서버가 조회 대상을 본인으로 강제합니다. 또 AI가 연차 신청·공지 작성 같은 쓰기 작업을 제안할 때는 초안만 만들고, 사용자가 확인 카드를 눌러야 기존 도메인 서비스를 통해 실제로 반영되게 했습니다. 백엔드는 NestJS + PostgreSQL + Prisma, AI는 Gemini 2.5 Flash Function Calling이고, Docker로 Railway에 배포했습니다."

## 15.2 기술적 난이도 — 강조할 3가지 포인트

### ① AI 계층에서의 권한 격리 (가장 차별화되는 부분)
- **문제**: LLM에게 DB 조회 도구를 주면, 사용자가 권한 밖 요청을 했을 때 LLM이 인자를 임의로 채워(타인 이름, 비워둔 필터 등) 권한 밖 데이터를 조회하려 할 수 있다.
- **해결**: 이중 방어.
  1. **노출 단계** — `RolePermission`에 해당 리소스 `READ` 권한이 없으면 도구를 LLM에게 주는 목록에서 제외(`AiToolsService.getDeclarations`). 쓰기 제안 도구(`draftAnnouncement` 등)는 실제 확정에 필요한 `CREATE/UPDATE` 권한자에게만 노출.
  2. **실행 단계** — LLM이 노출되지 않은 도구 이름을 직접 불러도 `execute()`가 권한을 다시 검사해 거부. `EMPLOYEE`는 인자로 넘어온 직원 이름을 무시하고 본인으로 강제(`resolveTargetEmployee`), 모든 쿼리에 `companyId` 스코프.
- **검증**: 위 동작은 단위 테스트로 고정(`ai-tools.service.spec.ts` — 권한 없는 도구 제외, 비노출 도구 직접 호출 거부, EMPLOYEE 타인 조회 차단, HR의 companyId 스코프).
- **왜 어려운가**: "프롬프트로 하지 말라고 지시"하는 수준이 아니라, **LLM이 무슨 인자를 보내도 서버가 신뢰하지 않는 구조**여야 한다는 점.

### ② AI가 데이터를 바꾸는 작업의 안전한 설계 — "제안 → 확인 → 확정"
- **문제**: AI가 "연차 신청해줘"를 받아 바로 DB를 수정하면, 오해석 한 번이 곧 잘못된 데이터가 된다.
- **해결**: AI 도구는 `AiActionDraft`(PENDING)만 만든다. 화면의 확인 카드를 사용자가 눌러야 확정되고, 10분이 지나면 만료된다. 확정 시에는 AI 전용 로직이 아니라 `LeaveService.create()`, `AnnouncementsService.create()`, `ProductionService.updateStatus()` 같은 **기존 도메인 서비스를 그대로 호출**하므로 수동 화면과 동일한 검증/트랜잭션을 탄다.
- **검증**: 초안 도구가 도메인 서비스를 호출하지 않는다는 점, 잘못된 휴가 유형/날짜/시간반차 누락은 초안 생성 전에 거부한다는 점, 생산 오더 변경은 담당자 본인 또는 ADMIN만 가능하다는 점을 테스트로 고정.

### ③ 재고/입출고/연차의 동시성 정합성
- **문제**: 동시에 여러 출고 요청이 들어오면 재고가 음수가 되거나, 같은 연차 잔액을 두 번 차감할 수 있다.
- **해결**: 재고 출고(`stock-movements`), 수주 출고(`sales-orders`), 연차 승인(`leave`)을 **Serializable 격리수준 `$transaction`** 으로 묶어 직렬화. 주문번호/사번 생성은 `count()+1` 경합으로 인한 unique 충돌(P2002)을 `retryOnDuplicate`(지터 재시도)로 흡수.

## 15.3 문제 해결 과정 (STAR 포맷 사례)

### 사례 1 — AI가 "다음 주 월요일"을 해석하지 못한 문제 (실제 발견·수정)
- **S**: 데모 중 일반 직원 계정으로 "다음 주 월요일 하루 연차 신청해줘"라고 했더니, AI가 신청 초안을 만들지 않고 "정확한 날짜를 알려달라"고 되물었다.
- **T**: LLM은 오늘이 며칠인지 모르는데 시스템 프롬프트에 현재 날짜가 없었다. 연차·매출("이번 달") 같은 상대 날짜 질의가 전부 불안정해질 수 있는 구조적 문제였다.
- **A**: 요청마다 KST 기준 오늘 날짜와 요일을 시스템 프롬프트에 주입(`buildSystemPrompt`)하고, 상대 날짜는 되묻지 말고 `YYYY-MM-DD`로 직접 계산하도록 규칙을 추가했다. 날짜가 UTC/KST 경계에서 하루 어긋나지 않도록 경계 케이스(UTC 20:00 → KST 다음 날 05:00)를 테스트로 고정했다.
- **R**: 같은 질문에 "다음 주 월요일(2026-10-19) 연차 신청 초안이 생성되었습니다"와 확인 카드가 정상 출력됐다.

### 사례 2 — AI 응답과 대시보드의 매출 숫자가 달랐던 문제 (실제 발견·수정)
- **S**: 같은 계정에서 대시보드 "이번 달 매출"은 ₩5,075,000, AI에게 물으면 ₩2,045,000이었다.
- **T**: 두 경로가 같은 데이터를 다르게 집계하고 있었다. 숫자 신뢰가 핵심인 ERP에서 치명적인 불일치.
- **A**: 원인은 대시보드 집계 쿼리가 `orderDate >= 이번 달 1일`만 걸고 **상한이 없어** 미래 날짜 주문까지 합산한 것. 월의 시작~다음 달 시작 미만으로 범위를 제한하고, 같은 문제가 재발하지 않도록 회귀 테스트를 추가했다. 같은 점검 중 재고 경고 목록의 React key 중복(같은 제품이 두 창고에 있을 때)과 차트 Y축 단위 오표기도 함께 수정했다.
- **R**: 대시보드와 AI 응답이 ₩2,045,000으로 일치했고, 브라우저 콘솔 에러가 사라졌다.

### 사례 3 — 비밀번호 재설정 링크가 "재사용 가능"했던 문제 (실제 발견·수정)
- **S**: 비밀번호 찾기를 구현한 뒤 실서버에 같은 재설정 링크를 두 번 호출해 봤더니, 두 번째도 `201 success`였다.
- **T**: 링크가 서명만 된 JWT(15분)라서, 한 번 쓴 뒤에도 만료 전까지 누구든 다시 써서 비밀번호를 바꿀 수 있었다(링크 유출 시 계정 탈취).
- **A**: 토큰에 **현재 비밀번호 해시의 지문(SHA-256 앞 32자리)** 을 함께 서명했다. 비밀번호가 바뀌면 지문이 달라져 같은 링크는 즉시 무효가 된다. 별도 저장소(Redis 등) 없이 1회용을 구현한 방식이다.
- **S2(부수 발견)**: 이 수정을 실서버로 확인하다가 500이 났다. 이 프로젝트는 Prisma 전역 설정으로 `passwordHash`를 기본 조회에서 **제외**하는데, 새 쿼리에서 명시적으로 켜지 않아 해시가 `undefined`였다. 단위 테스트의 목(mock)은 해시를 항상 돌려줘서 이걸 못 잡았다.
- **R**: 쿼리가 `omit: { passwordHash: false }`를 요청하는지까지 테스트로 고정했고, 실서버에서 `재설정 201 → 같은 링크 재사용 401 → 새 링크로 원복 201`을 확인했다. 교훈: 목 테스트가 숨기는 영역(ORM 전역 설정)은 실서버 확인이 필요하다.

### 사례 4 — Gemini 일시 장애(503)에서 사용자가 바로 오류를 보던 문제 (실제 발견·수정)
- **S**: AI 액션 확정 흐름을 검증하던 중 "AI 응답을 생성하는 중 오류가 발생했습니다"가 떴고, 서버 로그는 Gemini의 `503 UNAVAILABLE (high demand)`였다.
- **T**: 외부 API의 일시적 장애를 재시도 없이 그대로 사용자 오류로 노출하고 있었다.
- **A**: 429/5xx만 지수 백오프(1초→2초)로 최대 2회 재시도하고, 400/401/403처럼 재시도해도 소용없는 오류는 즉시 던지는 `retryTransient`를 만들어 Gemini 호출 3곳(채팅·FAQ 생성·문서 요약)에 적용했다.
- **R**: 재시도 판정/백오프/한도를 단위 테스트로 고정했다.

### 사례 5 — 완료된 생산 오더를 되돌렸다 다시 완료하면 재고가 두 번 입고되던 문제 (실제 발견·수정)
- **S**: 생산 오더 상태 변경 코드를 읽다가, 완료를 "진행중"으로 되돌릴 수 있고 재고는 그대로인 채 다시 "완료"하면 멱등 가드(`status != COMPLETED`)를 통과한다는 점이 보였다.
- **T**: 실제로 재현했다. 한 오더를 완료 → 되돌림 → 재완료하자 재고가 1,211 → 3,211 → 5,211로 늘고 입고 이력이 한 오더에 2건 생겼다.
- **A**: 완료·취소를 종착 상태로 만들어 되돌림을 서버가 409로 거부하고, 일반 상태 변경도 종착 상태가 아닌 행에만 조건부로 적용해 경합까지 막았다. 화면에서도 완료·취소 카드의 선택을 잠갔다.
- **R**: 거부/멱등 재완료/창고 없음/정상 입고 1회를 단위 테스트 7개로 고정했다. 같은 점검에서 데모 오더 10건이 입고 창고가 없어 완료 자체가 불가능한 시드 문제도 찾아 고쳤다.

### 사례 6 — AI 확정 경로가 권한 검사를 건너뛰던 문제 (실제 발견·수정)
- **S**: AI 초안은 "확정 시 기존 도메인 서비스를 그대로 호출해 동일한 검증을 탄다"고 설계했는데, 공지 작성 권한 검사는 서비스가 아니라 컨트롤러 가드에 있었다.
- **T**: DB에 일반 직원의 공지 초안을 직접 만들어 확정하자 **공지가 실제로 생성**됐다. 정상 흐름에선 직원이 공지 초안을 만들 수 없어 바로 악용되진 않지만, 초안 생성 뒤 10분 안에 권한이 회수돼도 확정되는 구조였다.
- **A**: 확정 시점에 액션별 필요 권한(`ANNOUNCEMENT:CREATE`, `PRODUCTION:UPDATE`)을 다시 검사하도록 했다. 연차는 본인 self-service라 제외했다.
- **R**: 같은 시나리오가 403으로 막히는 것을 실서버로 확인했고, 권한 있음/없음/연차 예외를 테스트로 고정했다.

### 사례 7 — 일정 추가 후 달력 선이 끊겨 보이던 CSS 문제 (실제 발견·수정)
- **S**: 일정을 추가하면 달력의 세로 구분선과 회색 배경이 날짜 숫자 부분에서만 그려지고 끊겨 보인다는 제보가 있었다.
- **T**: 원인은 `grid-template-rows: auto repeat(0, auto) 1fr`. 여러 날 일정(바)이 없는 주는 반복 횟수가 0인데 CSS의 `repeat()`는 1 이상이어야 해서 선언 전체가 무효가 되고, 배경 칸(`grid-row: 1 / -1`)이 첫 줄만 덮었다. 바 없는 주가 대부분이라 일정을 추가하면 눈에 띄었다.
- **A**: 반복 문법을 쓰지 않고 `auto` + (바 개수만큼 `auto`) + `1fr`로 직접 만들었다.
- **R**: 모든 주에서 배경 칸 높이와 주 높이가 같아지는 것을 측정으로 확인했다.

## 15.4 AI 적용 이유

- **단순 자동화가 아니라 "접근성" 문제 해결**: 중소기업 ERP의 실제 문제는 기능 부족이 아니라 "어디에 뭐가 있는지 모름"이다. 자연어 인터페이스는 메뉴 구조를 외울 필요 없이 원하는 데이터에 바로 도달하게 한다.
- **조회뿐 아니라 "행동"까지 — 단, 사람이 최종 확정**: 연차 신청·공지 작성·생산 상태 변경을 AI가 초안으로 만들어 주고 사람이 확인한다. 편의성과 안전성을 동시에 가져가는 지점.
- **보안을 타협하지 않는 AI 도입이 실무의 가장 큰 허들**이라고 판단했다. 기업이 AI ERP 도입을 주저하는 핵심 이유가 "권한 우회/데이터 유출"이므로, 이를 정면으로 설계에 반영한 것이 이 프로젝트의 설득력이다.

## 15.6 보안 고려사항

1. **다층 권한 검증**: 화면(Route Guard) → API(`JwtAuthGuard` + `PermissionsGuard`) → AI 도구(노출 필터 + 실행 시 재검증) 3중 강제.
2. **토큰 보안**: Access Token은 짧은 만료, Refresh Token은 httpOnly + SameSite 쿠키에 **해시로만 저장**하고 갱신마다 폐기·재발급(Rotation). 비밀번호 변경 시 이전 refresh 토큰 무효화. 비밀번호 재설정 링크는 15분·**1회용**(현재 비밀번호 해시 지문에 묶임)이며, 존재하지 않는 이메일에도 같은 응답을 줘 계정 존재 여부를 숨긴다.
3. **멀티테넌시 격리**: 모든 조회에 `companyId`를 서비스 레이어에서 강제. (DB 레벨 RLS는 **미구현** — 확장 과제)
4. **AI 특화**: 도구 호출 한도(턴당 4회), 모델이 만든 FAQ 임계치/중복 여부를 서버가 재검증, 쓰기 작업은 초안→확인 구조.
5. **감사 추적**: 급여 확정, 권한 변경, 재고/출고 등 민감 액션에 `@Audit` 데코레이터로 `AuditLog` 기록.
6. **기본 방어**: `helmet`, 전역 `ThrottlerGuard`(분당 300회, 로그인·재설정·refresh는 5~10회로 더 좁게), 약한 JWT 시크릿은 부팅 시 검증 실패 처리.

## 15.7 예상 질문 & 답변

**Q. 문서 검색은 RAG인가요?**
> A. 현재는 **제목/요약 키워드 검색**입니다. 설계 단계에서는 pgvector 유사도 검색 RAG(문서 10·11)를 그렸고 스키마(`vector(1536)`)도 준비해 두었지만, 임베딩 파이프라인·큐 인프라를 포함하면 범위가 커져서 "권한 인지 검색"이라는 핵심 가치를 먼저 증명하는 단순 경로로 구현했습니다. 다음 단계는 임베딩 색인 + `WHERE companyId/공개범위` 조건을 포함한 유사도 검색입니다.

**Q. LLM이 잘못된 함수를 호출하거나 인자를 잘못 생성하면 어떻게 되나요?**
> A. 두 가지로 방어합니다. 권한이 없는 도구는 목록에서 제외돼 호출 시도 자체가 안 되고, 설령 이름을 직접 불러도 실행 단계에서 권한을 다시 검사합니다. 인자도 신뢰하지 않아서, 예를 들어 일반 직원이 타인 이름을 넘겨도 서버가 본인으로 강제합니다. 이 동작은 테스트로 고정해 두었습니다.

**Q. AI가 실수로 데이터를 바꾸면요?**
> A. AI는 직접 쓰기를 못 합니다. 초안만 만들고 사용자가 확인을 눌러야 하며, 확정 시에는 수동 화면과 같은 도메인 서비스를 호출해 같은 검증을 통과해야 합니다. 초안은 10분 뒤 만료됩니다.

**Q. 토큰 비용은 어떻게 관리했나요?**
> A. 키워드로 관련 도구만 먼저 좁혀 노출하고, 컨텍스트를 최근 10턴, 턴당 도구 호출을 4회로 제한했습니다. 응답마다 사용 토큰을 기록해 화면에서 볼 수 있게 했습니다. 설계 단계의 "저비용 모델로 분류 후 메인 모델 호출"은 LLM 호출이 한 번 더 늘어 키워드 라우팅으로 단순화했습니다.

**Q. 멀티테넌시는 어떻게 검증했나요?**
> A. 모든 마스터 테이블에 `companyId`를 두고 서비스 레이어 쿼리에 강제 포함합니다. AI 도구 쿼리도 마찬가지이고 단위 테스트로 스코프 조건을 검증했습니다. DB 레벨 RLS는 아직 적용하지 않았고, 애플리케이션 버그에 대한 2차 방어로 다음에 추가할 항목입니다.

**Q. 동시 출고는 어떻게 처리했나요?**
> A. 재고 출고·수주 출고·연차 승인을 Serializable 트랜잭션으로 묶어 음수 재고와 이중 차감을 막았고, 번호 채번 경합은 unique 충돌 재시도로 흡수했습니다.

**Q. 이 프로젝트에서 가장 어려웠던 부분은?**
> A. "편의성(AI가 뭐든 해주는 것)"과 "보안(권한 밖은 절대 안 됨)"의 균형입니다. 그리고 데모를 직접 돌려보다 AI 응답과 대시보드 숫자가 다른 걸 발견해 원인을 추적한 경험이 있습니다. AI 기능일수록 "눈으로 확인 + 테스트로 고정"이 중요하다고 느꼈습니다.

## 15.8 5분 발표 스크립트 (전체본)

> 안녕하세요, ERPilot이라는 AI 기반 ERP SaaS 플랫폼을 소개하겠습니다.
>
> 중소기업 ERP 현장에서 가장 흔한 불편은 "어디서 뭘 찾아야 할지 모른다"는 것입니다. 재고를 확인하려고 메신저로 담당자를 찾거나, 연차 신청 메뉴를 찾아 헤매는 식이죠. ERPilot은 이런 업무를 자연어 한 문장으로 해결하는 AI 업무 도우미를 ERP 코어에 결합했습니다. 예를 들어 "재고 부족한 품목 알려줘"라고 하면 실제 DB를 조회해 답하고, "다음 주 월요일 연차 신청해줘"라고 하면 신청 초안을 만들어 확인 카드를 띄웁니다.
>
> 기술적으로 가장 신경 쓴 부분은 AI의 보안입니다. LLM에게 DB 접근을 준다는 건, LLM이 잘못된 인자를 보내도 안전해야 한다는 뜻입니다. 그래서 권한이 없는 도구는 모델에게 아예 보여주지 않고, 모델이 어떤 인자로 도구를 호출하든 서버가 실행 직전에 사용자의 실제 권한으로 다시 검증합니다. 일반 직원이 타인의 근태나 급여를 물어도 조회 대상은 본인으로 강제됩니다. 이 동작은 단위 테스트로 고정해 두었습니다.
>
> 두 번째는 쓰기 작업의 안전성입니다. AI는 연차 신청이나 공지 작성을 직접 하지 않고 초안만 만들며, 사용자가 확인을 눌러야 기존 도메인 서비스를 거쳐 실제로 반영됩니다. 수동으로 신청하는 것과 완전히 같은 검증 경로를 타기 때문에 AI가 우회로가 되지 않습니다.
>
> 개발 중에는 직접 데모를 돌려보다 문제를 두 개 찾았습니다. AI가 "다음 주 월요일"을 못 풀어서 오늘 날짜를 프롬프트에 주입했고, 대시보드 매출과 AI 답변이 달라서 추적해 보니 집계 쿼리에 월 상한이 없었습니다. 둘 다 회귀 테스트로 고정했습니다.
>
> 인프라는 NestJS와 PostgreSQL을 중심으로 Docker 멀티스테이지 빌드를 만들어 Railway에 프론트/백엔드를 각각 배포했고, GitHub Actions로 린트·빌드·테스트를 자동 검증합니다. 설계 단계에서는 pgvector 기반 RAG와 AWS 배포까지 그렸지만, 범위를 줄여 키워드 검색과 Railway로 구현했고 그 트레이드오프도 문서로 남겼습니다.
>
> 결론적으로 ERPilot은 "AI를 붙인 ERP"가 아니라 "ERP의 권한 모델을 AI 계층까지 일관되게 확장한 시스템"이라는 점이 가장 차별화되는 포인트라고 생각합니다.
